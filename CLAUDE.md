# Tally: instructions for AI sessions

- **Multi-agent mode (from 2026-10-03):** if you were given a work order in `docs/work-orders/`, also follow `AGENTS.md`, and treat `MODULES.md` (v2) as the module plan. Touch only the paths your work order owns.
- **Start by reading** `TALLY_BLUEPRINT.md` (end to end), then `DESIGN.md`, then `IDEAS.md` §Findings F1–F11. The decisions in blueprint §4 are final unless new evidence contradicts them; propose changes, don't make them silently.
- **Build in milestone order** (blueprint §17). Before coding a milestone, list its tasks and exit checks. A milestone is done only when every exit check passes.
- **Never create, request, print or store private keys or seed phrases.** The user creates the ShareGuard deployer/owner key and the Ondo feed-signer key and runs deployments on their own machine (blueprint §19). Secrets live only in the server's env file, never in git.
- **Never deploy spike code.** `spike/shareguard/src/ShareGuard.sol` has a known arbitrary-call hole; ShareGuard v1 must allow-list routers (blueprint §10, fork test G).
- **UI:** follow `DESIGN.md` exactly. Use beUI components via the BeUI MCP and restyle them with our tokens. Every screen is checked at 375/768/1280px and with reduced motion before it counts as done.
- **Where code runs:** cloud build sessions run in a US data centre (checked 2026-10-01: Google Cloud, Illinois), and the authenticated Binance Web3 API refuses US callers (`40304`). So in cloud sessions, develop and test against recorded fixtures (`spike/results/`, `research/snapshot-*/`, plus new ones the user records). Public `bapi` endpoints and BSC RPC do work from the cloud. Anything that needs the authenticated API live (quotes, swap calldata, live buys) is run by the user on the **AWS Seoul EC2**, which also hosts the app. Give the user exact commands to run there and ask them to push the output.
- **Binance Web3 API:** errors can arrive as HTTP 200, so always check the JSON `code`. Never trust the API's `gas` (always 450000); estimate and simulate at the exact limit you send. The minimum order is 6 USDT.
- **Don't rename** the old `parity` identifiers inside `spike/` and `research/` (historical; the fork test's fixed address is derived from `"parity.shareguard.fork"`).
- **Git:** one branch and one PR per milestone. Keep `main` deployable.
- **The Developer Experience Report is written by the user**, not by an AI (the hackathon rejects AI-generated reports). You may point to evidence in `IDEAS.md`.
- Never add Co-Authored-By or Claude-Session lines to commits or PRs.

## Repo state and conventions (updated during M2, 2026-10-02)

- **Status:** M0 and M1 merged. **M2 (ShareGuard v1) is done: deployed and verified at `0x28F6F19bffbF25E36452c78d12090F0bC922970a` (BSC, 2026-10-02), two live guarded buys recorded (`IDEAS.md` §F11).** **M3 (web trade flow) is built on `claude/m3-web-trade-flow`; the exit checks that need real money (the phone test, live trade plan on the EC2) are the user's. See "Web trade flow (M3)" below.** Milestone results live in `IDEAS.md` §F9 (M0), §F10 (M1) and §F11 (M2); the M0 provider review is in blueprint §9. `SHAREGUARD_ADDRESS` is the deployed address; the owner/deployer is the user's own wallet and the Ondo feed signer is `0xDd3C5F463d71fb06D7bE749F904A4090E080f407` (its key goes in the server env only in M3).
- **Layout:** pnpm workspaces on Node 22. `apps/web` (Next 16, standalone output); `apps/bot` and `packages/mcp` are typed stubs until their milestones; `packages/config` holds the region block list and constants.
- **Engine (M1):** `packages/core` is pure (bigint share maths, multiplier resolution and Ondo bounds, integrity grade, gas model, TTL cache, registry, `consolidatedQuote` against injected ports). `packages/binance` is the signed client (pacing, retries, HTTP-200 error codes, zod schemas, typed endpoints, public API, fixture transport) and implements core's ports in `adapters.ts`. `packages/chain` is viem with failover, multiplier readers, `planGas` (×1.25) and `simulateAtLimit`. `packages/engine` wires them and holds the CLI. Web, bot and MCP must call `@tally/engine`, never rebuild the wiring.
- **CLI:** `pnpm tally quote NVDA 25 --fixtures` (offline, works anywhere), `pnpm tally ladder NVDA --fixtures`, `pnpm tally facts NVDA` (every token's readings, baseline and integrity log), `--shares`, `--json`, `--checks` (print the integrity log under the quote), `--blocked` (simulate 40304). Use `pnpm --silent tally …` when redirecting output, or the pnpm banner lands in the file. Without `--fixtures` it needs `BINANCE_W3_API_KEY`/`BINANCE_W3_API_SECRET` and only works from the Seoul EC2.
- **Fixtures:** `packages/binance/fixtures/raw/` holds raw recordings (excluded from Prettier: never reformat or edit them). Recorders live in `spike/`: `record_m1_fixtures.py` (quotes, errors, swap builds), `record_region_block.py` (run from a blocked IP with a valid key), `record_m1_probes.py` (paging, Market/Transaction/Wallet paths; already run, output in `probes_*.json`). Fixture-mode engines replay "as of" `FIXTURE_NOW` (2026-10-02 05:26 UTC), not the wall clock. Run them on the Seoul EC2 and push the output; new tests should use the newest file of each kind.
- **Integrity log:** every integrity check writes a record (inputs, outcome pass/deduct/flag/skipped, one-line summary) whether or not it costs points, and a fact that is missing carries the reason (`TokenMarketFacts.notes`), which also appears in the quote's `warnings`. Never add a check or a fallback that can fail silently. The attestation rule is calendar days > 3 until a few days of EC2 `tally facts` data say otherwise.
- **Ondo multiplier baseline:** `data/ondo-multiplier-baseline.json` (value + seenAt per token, seeded from the 09-30 snapshot by `packages/engine/scripts/seed-ondo-baseline.ts`) is the committed read-only seed. Live engines write a runtime copy to `$TALLY_DATA_DIR/ondo-multiplier-baseline.json` (or `TALLY_BASELINE_PATH`); with neither set the store is read-only, so the repo is never dirtied. Only readings that pass the bounds are recorded: one increase ≤ 3% (a judgement threshold; the largest measured step is +0.58%) unless the price check fails; a decrease or an increase above 3% only with all three of (1) a `stock_split`/`stock_dividend` status within 48 h (`reasonMsg` is a bare code, no ratio is read from it; sightings are kept in the same file), (2) new/old within 0.5% of a simple ratio, (3) tokenPrice ÷ newMultiplier within 2% of `stockInfo.price` once trading has resumed. The price check also runs on every other multiplier change and is logged as `multiplier-validation`. Otherwise the token stays blocked and flagged; the owner's manual action is only a fallback. SQLite replaces the file later.
- **Data rules learned in M1:** the reference price is `referencePrice ÷ tokenToShareRatio` (per token in the list, not per share); the authenticated RWA list is truncated and has no xStocks, so the registry comes from the public lists; every data-source fallback must call `onWarn` (silent fallback once hid a schema bug); a token with under $1,000 of 24h on-chain volume is a ghost and is not executable, even for Ondo (NFLXon had $16). Commands: `pnpm typecheck`, `pnpm lint`, `pnpm format:check`, `pnpm test`, `pnpm build`, `pnpm e2e`, `pnpm tally` (Playwright needs the standalone build first).
- **Next 16 renamed middleware to `proxy.ts`.** The region gate lives in `apps/web/proxy.ts` and answers blocked visitors directly with a 451 (`lib/blocked-page.ts`). Do not turn it back into a rewrite: behind a Cloudflare tunnel the request URL is `https://localhost:3000` and the rewrite fails with `EPROTO` (regression test in `e2e/region-gate-tunnel.spec.ts`). The gate fails closed without `cf-ipcountry`; set `TALLY_ALLOW_MISSING_GEO=1` only for local dev and tests.
- **Env files:** Next reads `apps/web/.env.local`, not a repo-root `.env`. `NEXT_PUBLIC_*` values are inlined at build time, and `next dev` must be restarted after editing them. The Privy App ID is public (`NEXT_PUBLIC_PRIVY_APP_ID`); the App Secret is never needed in the browser app.
- **Cloud sandbox quirks:** `forge` lives at `~/.foundry/bin` (add it to PATH; `foundryup` downloads are blocked by the proxy). The pre-installed Chromium is older than Playwright 1.63 expects, so run e2e with `PLAYWRIGHT_CHROMIUM_PATH=/opt/pw-browsers/chromium` (CI downloads its own). Kill a stale local server with `fuser -k <port>/tcp`, not `pkill -f` on a pattern that also matches your own shell.
- **Testing the region gate for real:** run the production build behind `cloudflared tunnel --url http://localhost:3000` and open the URL from another device or a browser-only VPN. A VPN on the machine running `cloudflared` breaks the tunnel (Cloudflare 524 timeouts); that is the test setup, not the app.
- **Wallet check page removed (start of M1).** `/dev/wallet-check` and `NEXT_PUBLIC_ENABLE_WALLET_CHECK` are gone; the M0 wallet results stay in `IDEAS.md` §F9. `components/providers.tsx` is gone: the wallet layer is `components/wallet/` (see the M3 section). ## ShareGuard v1 / contracts (M2)

- **Layout:** `contracts/` is Foundry (Solidity 0.8.28, evm `prague`; OpenZeppelin 5.4 and forge-std are git submodules, so clone with `--recurse-submodules`). `src/ShareGuard.sol` is the contract; `test/` has unit, fuzz and fork tests A–I; `script/Deploy.s.sol` deploys; `tools/gen_assets.py` builds the deploy inputs; `tools/guarded_buy.py` does the live guarded buys; `contracts/README.md` has the exact commands. Never deploy `spike/shareguard/` or `contracts/test/SpikeVulnerable.sol`.
- **Commands (sandbox):** `export PATH=$HOME/.foundry/bin:$PATH; cd contracts; forge test` (offline; the fork tests skip), `./script/fork.sh` (fork tests A–I on every capture; needs the archive `BSC_RPC`, which is set in the cloud sandbox and works), `forge fmt`, and a key-less deploy dry run: `FEED_SIGNER=0x…dEaD forge script script/Deploy.s.sol:Deploy --rpc-url $BSC_RPC --sender 0x1111111111111111111111111111111111111111` (run `python3 tools/gen_assets.py NVDA AAPL TSLA QQQ SPY` first; seeds expire after 2 h).
- **Fork tests pin to the capture's block** (archive RPC), so committed captures in `contracts/captures/` replay without a Binance key from the cloud. Fresh captures come from the Seoul EC2 (`./script/capture.sh`).
- **Foundry gotchas hit in M2:** `vm.expectEmit` and `vm.expectRevert` bind to the *next call*, and so does `vm.prank`; an argument like `guard.toShares(...)` is an external call that consumes it. Compute such values first. Long external calls hit "stack too deep" in tests: wrap them in a helper rather than enabling `via_ir`.
- **Pause checks:** bStock has no pause getter; its shared manager `0x9fc7…700a` is stored per asset. Ondo's manager is read from the token each swap. Both fail closed. See `IDEAS.md` §F11.
- **Keys:** `DEPLOYER_PK` is read only by the user's own forge run; `PARITY_PK` (buyer burner) and `FEED_SIGNER_PK` only by `tools/guarded_buy.py` on the user's EC2. Never create, print, store or ask for them; the fork tests use public test constants (`0xA11CE`, `0xFEED5`) only.

## Web trade flow (M3)

- **Trade plan:** `@tally/engine` `engine.trade.prepare({ticker, issuer, usd, tolerancePct, user})` (`packages/engine/src/trade.ts`). It re-quotes every call and answers one of `needs_funds` (shortfall), `needs_approval` (exact-amount `approve(guard, amountIn)`), or `ready` (guard calldata, gas = `eth_estimateGas` from the user × 1.25, simulated at that exact limit with `eth_call` and Binance's simulate; Binance's simulate failing is a warning, not a gate). The web calls it again after the approval mines and when `expiresAt` (15 s) passes. `engine.trade.receipt(hash, ticker)` decodes the guard's `Guarded` event. Errors are `TradeError` kinds (`price_moved`, `token_paused`, `feed_stale`, `rfq_required`, ...), mapped to plain words in `explainRevert` and `apps/web/lib/server/http.ts`.
- **Ondo feed signer:** there is no separate sign endpoint. `prepareTrade` signs a bounded `FeedUpdate` itself, only when the guard's stored value is stale or differs from the engine's accepted multiplier by more than 1 ppm. `FEED_SIGNER_PK` is read only by `feedSignerFromEnv` on the server. Tests use a public test constant (`0xfeed5`), never a real key.
- **Fixture mode:** `TALLY_FIXTURES=1` runs the whole app offline (recorded Seoul quotes for NVDA, AAPL, NFLX at 6/25/100/1000; no TSLA/QQQ/SPY quotes recorded, so those tickers fail in fixture mode only). `fixtureTradeChain` fakes the wallet and guard; the pseudo hashes `FIXTURE_APPROVE_HASH`/`FIXTURE_SWAP_HASH` answer receipt polls. The browser test hook is `window.__tallyMockWallet = {address, signedIn}` (`components/wallet/wallet-context.tsx`): a fake wallet that returns those pseudo hashes. It cannot move money.
- **Web layout:** `/api/{quote,trade/plan,trade/receipt,fills,declaration,health}` (zod-validated, per-IP limits; `TALLY_RATE_LIMIT_MULT` raises them for tests); `lib/server/engine.ts` (one lazy engine, sets `TALLY_REPO_ROOT` so a bundled server finds `data/` and the fixtures); `components/trade/*` (trade card, issuer list, `use-trade-flow` state machine, sheets, receipt); `components/wallet/*` (Privy loaded lazily, BSC only, `showWalletUIs: false` because Tally shows its own confirm step; a deliberately connected external wallet wins over the embedded one). Only NVDA, AAPL, TSLA, QQQ and SPY are buyable (`lib/tickers.ts`): those are the assets ShareGuard was deployed with.
- **UI names and pages (owner decision 2026-10-02):** tagline "Buy tokenized shares, at the best prices" (never imply users buy the underlying shares; say "tokenized shares"). The product pages are **Home** `/` (minimalist trade card plus one screen each for Trade, Portfolio and Radar, then the FAQ), **Trade** `/trade[/TICKER]` (the full flow; advanced features shown as "Soon"), **Portfolio** `/portfolio` and **Radar** `/radar` (the old Trap Shield). `/docs` holds the contract links and proof; it is linked from the footer, and **no contract address is linked anywhere else in the UI** (transaction links on receipts are fine). UI copy says "the guarantee", not "ShareGuard"; the contract and code keep their names. Domains: `trytally.xyz` will be the landing page (built last), `app.trytally.xyz` this app. Selling or swapping tokenized stocks to BNB/USDT is shown disabled ("Soon"): the deployed ShareGuard only buys.
- **Wallet state never remounts the page:** `WalletRoot` (in `app/layout.tsx`) keeps `children` under one context provider and the lazily loaded Privy bridge pushes state in through `onChange`. Swapping the provider around `children` once wiped typed amounts and tabs when the SDK finished loading. Dialogs are the centered `components/motion/modal.tsx` (scroll lock is `overflow: hidden`, not a fixed body); `Segmented` and the FAQ tabs use `layoutRoot` so their pills never replay page shifts.
- **Third-party UI:** `components/spectrumui/faq-tabs-card.tsx` is Spectrum UI's FAQ Tabs Card (Apache-2.0), taken from its public registry JSON `https://ui.spectrumhq.in/r/faq-tabs-card.json` (the docs page hides the code behind a login) and re-skinned.
- **Env:** everything is in `/etc/tally/tally.env`, including `NEXT_PUBLIC_PRIVY_APP_ID` (load the file before `pnpm build`). The code reads `BSC_RPC_PRIMARY`, not `BSC_RPC_URL`. `SHAREGUARD_ADDRESS` defaults to the deployed address. `TALLY_DATA_DIR` holds the Ondo baseline, `fills.jsonl` and `declarations.jsonl`.
- **CSS gotchas hit in M3:** unlayered rules in `globals.css` (`.glass { position: relative; background }`, `.btn { display }`) beat Tailwind utilities, so `fixed`/`hidden` on those elements silently did nothing (the bottom sheet rendered at the page bottom). Use `!fixed`, `!bg-…`, or wrap. A grid with no `grid-cols-1` sizes its track by min-content and overflows a 375px screen: give grids `grid-cols-1` and children `min-w-0`. `BottomSheet` keeps `onOpenChange` in a ref: parents re-render every second and the old effect stole focus each time.
- **Round 2 UI decisions (owner, 2026-10-03):** nav is Trade, Portfolio, Radar, How it works (`/docs#how`); the FAQ is a Home section and a footer link only. "How it works" stays in the nav and footer permanently; the hero buttons (Get Started, How it works) disappear once signed in, and the nav "Get Started" becomes the short wallet address with a menu (Copy, Send, Export wallet, Portfolio, Sign out). The Home trade card's button is "Get Started" until sign-in, then it is the transaction (`flowActionLabel` in `components/trade/flow-host.tsx`: Buy, Approve, Confirm, Buying, Bought); Sell, Sell to BNB and Migrate between issuers are shown disabled. Stock dropdowns are beUI's Select (`components/motion/select.tsx`, unchanged) with glass classes, offering only the five buyable stocks. `SendModal` sends USDT or BNB out of the signed-in wallet; `exportWallet` opens Privy's own export dialog (Tally never sees the key). The progress pill is beUI's dynamic-island on a glass shell and mounts only while a buy is under way; `DynamicIsland` snaps to its size on first show (it used to spring open from a pill, which clipped the text) and takes a `contentClassName` minimum width.
- **Wallet bridge rule:** never put Privy's functions (`sendTransaction`, `login`, ...) in the dependencies of the value pushed to the app: Privy returns new ones every render and the app loops forever (React error #185, "This page couldn't load"). Keep them in refs. The mock wallet bypasses Privy, so before pushing wallet changes run `NEXT_PUBLIC_PRIVY_APP_ID=clx0000000000000000000000 pnpm build && pnpm e2e` (the real-provider tests skip themselves on a build with no App ID). A wallet-provider failure is contained by `WalletBoundary`; `app/error.tsx` is the last resort.
- **Round 3 UI (owner, 2026-10-05):** live readings roll digit by digit (`components/motion/animated-number.tsx` is Spectrum UI's Number Ticker, Apache-2.0, adapted for decimals and strings; `components/motion/live.tsx` has `LiveUsd/LiveShares/LivePct/LiveNumber`), and `useJson(url, {refreshMs})` polls while the tab is visible (Portfolio every 10 s, quotes every 10 s). "Read more" links use `lib/concepts.ts` + `components/learn-more.tsx` (fade/blur modal, ends in a link to `/docs#how-<concept id>`; the docs page lists every concept as a placeholder anchor until the How it works write-up exists). Every tag has a tooltip (`components/ui/tooltip.tsx`, `Tip`; pass `focusable={false}` when the tag sits inside a button). Names: Liquid (A or B), Low Liquidity (C to F), Not Tradable (ghost market), Min amount to receive, Slippage. Body text is weight 500 and every text size is +1px (Tailwind `--text-*` scale overridden in `globals.css`). Select items share one gliding highlight. Send validates through `lib/address.ts` (`checkRecipient`). The desktop account menu is `components/motion/morph-menu.tsx` (portal, fixed, morphs from the button, no scroll lock); mobile keeps the bottom-sheet menu.

- **Never write `-webkit-backdrop-filter` by hand in CSS.** The Tailwind/lightningcss build kept only the prefixed line when both were written, and Chrome ignores the prefixed form alone, so every blurred surface lost its blur in production Chrome. Write plain `backdrop-filter` and let the build add the prefix.
