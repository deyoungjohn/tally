# WO-07: sales fail on chain with RFQ_OrderExpired (found by the chief engineer, 9 Oct)

Same worktree and branch as WO-07/WO-13 (fast-forward to `main` first; PR 61 has merged). No new branch; commit, push, open a new PR from the same branch.

## Evidence
Three sales of TSMB from the Privy wallet were mined and **reverted** at the LiquidMesh router (`0xB444…DDA5`), at 11:05, 11:07 and 11:08 UTC on 9 Oct (hashes `0xf555979e…`, `0xa04ac844…`, `0x5f88bcfa…`). Gas used about 372k of 646k, no logs, nothing sold. Replaying the second one one block before it was mined gives `execution reverted: adapter:0x7977…:Error(RFQ_OrderExpired …)`; the other two replay fine one block earlier, so their order expired in the block they were mined in. The server's plan for the same sale was `ready` with both simulations `ok`. Conclusion: for this token the best route is a market maker (RFQ) order whose validity is only a few seconds. The plan, the Privy signature and the mining together outlast it. (The TSMB buy proof used `Rfq Neptunex:TSMB`; the buy path is off limits, see below.)

## Do (sell path only: `packages/engine/src/sell.ts`, the sell sheet and `use-sell-flow.ts`, and their tests)
1. **Prefer a pool route over an RFQ route for a direct, user-signed sale.** `quoteRoutes` returns every route; `pickBest` (shared with the buy path, do not change it) takes the highest output. In `sell.ts`, among the routes returned, identify RFQ routes (their route or adapter name contains `Rfq`; read the recorded quotes in `packages/binance/fixtures/raw/` and `spike/results/` for the exact field, do not guess) and choose the best non-RFQ route when its output is within 0.5% of the best RFQ output. When only an RFQ route exists, or it is better by more than 0.5%, use it and set `plan.rfq = true` plus a plain warning.
2. **Sign fast for RFQ.** When `plan.rfq` is true, the sheet must not add any step between the fresh plan and the wallet request: fetch the plan on Confirm, then send immediately (no extra render waits, no second estimate). Keep the existing rule that Confirm signs only a fresh plan.
3. **Explain a reverted sale.** The sheet already watches the transaction through `/api/trade/tx-status`. When the status is reverted, show plainly: "The sale did not go through. Nothing was sold; only the network fee was spent. Market-maker quotes last a few seconds. Try again." with a "Try again" button that re-plans. Never claim a reason the chain did not give; if the plan was `rfq`, say "likely because the market-maker quote expired", otherwise just that it did not go through.
4. **A single, user-triggered retry only.** No automatic second transaction.
5. **Buys:** the buy path (ShareGuard buys) uses the same routes and can fail the same way. It is off limits to you. In the PR, report whether the recorded buy quotes show RFQ routes and how often, so the chief engineer can decide.
6. Tests: route choice (pool within 0.5% beats RFQ; RFQ better by more than 0.5% is used and flagged; only-RFQ is used and flagged; no route errors as today), the revert message with and without `rfq`, and an e2e with the mock wallet for a reverted sale and the retry. Existing sell, Migrate and receipt tests stay green.
7. Report the real `FULL=1 bash scripts/review-pack.sh <branch>` output; run it when the machine is quiet.
