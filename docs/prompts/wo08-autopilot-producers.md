## Why
Autopilot shadow mode has nothing to decide on because no one writes its two inputs: `autopilot-position/<wallet>:<token>` and `autopilot-policy/<wallet>`. This slice adds both producers, so the user can set a policy in the UI and the shadow log shows real decisions.

## 1. Position collector (inside the existing `autopilot` job: no new process, the EC2 has 1.9 GB)
At the start of each `autopilot` run, before `runShadow`, refresh positions **only for wallets that have a stored policy** (opt-in, so cost stays bounded): for each wallet and each token in its `tokenAllowList`, write one `autopilot-position/<lowercase wallet>:<lowercase token>` snapshot with:
- `chainBalanceTokens` from the **chain** (the engine's existing read-only holdings or `sharesOf` accessors, the same source the sell flow uses; **never** `baw`'s or Binance's displayed balance) and `balanceSource: "chain"`; `tokenDecimals` read from the token (18 for these assets, but read it);
- `multiplier` the engine's **accepted** multiplier (E18), `shares` from the existing share maths (bigint, never 1:1; unknown stays `null` with the reason in a warning), `usdPerShare` (E18) from the existing reference price per share (`referencePrice` divided by the recorded token-to-share ratio, as `mod-statement` and `mod-pies` do);
- `grade` from the engine's existing integrity grade, `paused` from `engine.pauseState`, and `pausedSince`: track the **continuous** pause start yourself in the store (a small `autopilot-pause` snapshot per token: set when first seen paused, cleared when seen unpaused; an unknown reading neither sets nor clears it);
- `observedAt` now. Any unreadable fact is `null` (the decision then refuses with its reason); nothing is fabricated or defaulted.
A failure for one token warns and skips that token only; a failure of the whole collector throws before `runShadow` writes anything, so the log stays unchanged. The collector must respect an abort signal and the job's 30 s timeout. Cap the work: at most 20 wallets and 10 tokens per wallet per run, with a warning when truncated.

## 2. Policy writer (verified session only)
New routes, all `force-dynamic`, flag `autopilot` (404 when off), per-IP and per-user rate limits (policy writes: 20 per hour per user), wallet **only** from `verifiedWallet(req, x-tally-wallet)`; never from the query, cookie or body:
- `GET /api/session/autopilot/policy` returns the current `PolicySettings` (bigints as strings), the code ceilings and defaults, and the status of each position the collector last wrote (token, shares, USD value, grade, paused, age). 401 `session_required` without a verified wallet.
- `PUT /api/session/autopilot/policy` validates the body with zod and stores a new `autopilot-policy/<wallet>` snapshot (source `web-session`). Rules: `killSwitch` boolean **defaulting to `true` when omitted**; `armedRules` only the three known rules with sane bounds (pause hours 1 to 720, grade `D` or `F`, a positive USD stop per share as a decimal string); `perTradeCap` and `dailyCap` decimal USD strings that are **rejected, not clamped,** above the code ceilings ($100 and $250) and below the 6 USDT minimum; `tokenAllowList` limited to **at most 10 addresses that exist in the registry snapshot as an executable bStock or Ondo token** (xStocks and unknown addresses rejected with the reason). Unknown fields are rejected. Return the stored policy.
- A change history: keep every saved policy as its own snapshot (do not overwrite or prune); the shadow job already reads the latest. Add a one-line note in the README that `autopilot-policy` is not an evidence kind and may be pruned by retention, and say what that means for audit.
